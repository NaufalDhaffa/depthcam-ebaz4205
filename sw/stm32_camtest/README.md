# OV7670 tester — STM32F446RE Nucleo-64

A standalone functional check for the OV7670 modules, deliberately
independent of the FPGA. The point is to get a **known-good reference** for
what the camera actually produces, so a bad image on the EBAZ4205 can be
attributed to the FPGA design rather than guessed at.

Built with nothing but `arm-none-eabi-gcc` — no CMSIS, no vendor SDK, no
Eclipse workspace to reproduce.

## Wiring

| OV7670 | Nucleo | Note |
|---|---|---|
| 3V3 | 3V3 | **not** 5V |
| GND | GND | |
| PWDN | GND | strapped low = always awake |
| RESET# | 3V3 | strapped high = never reset |
| XCLK | PA8 | 16 MHz, generated by the MCU (MCO1 = HSI) |
| PCLK | PA9 | |
| VSYNC | PA10 | |
| HREF | PA11 | |
| D0..D7 | PC0..PC7 | contiguous, so a whole pixel byte is one register read |
| SIOC | PB8 | bit-banged SCCB |
| SIOD | PB9 | bit-banged SCCB |

Because PWDN/RESET# are strapped in hardware, a camera stuck in a bad state
can only be recovered by power-cycling — the firmware cannot pulse RESET#.

## Build and flash

```bash
cd sw/stm32_camtest
make
make flash          # openocd + ST-LINK/V2-1
```

## Use

The console is the ST-LINK virtual COM port (`/dev/ttyACM0`) at **921600 8N1**.
Drive it with the host script:

```bash
python3 sw/tools/ov7670_capture.py probe        # SCCB identity registers
python3 sw/tools/ov7670_capture.py activity     # PCLK/HREF/VSYNC edge counts
python3 sw/tools/ov7670_capture.py regdump
python3 sw/tools/ov7670_capture.py capture -o frame.png
python3 sw/tools/ov7670_capture.py stream         # live view, close window to stop
```

`stream` sends luma only (19200 bytes/frame instead of 38400), which is all
the grayscale comparison against the FPGA needs and roughly doubles the frame
rate. Measured end-to-end: **~1.24 fps** at 921600 baud.

That rate is dominated by the link and by waiting for the next VSYNC
boundary, not by anything fixable in software. Raising the camera's PCLK
would shorten the wait but squeeze the polled capture loop (only ~42 core
cycles per PCLK half-period at 1 MHz already), risking dropped pixels — not
a trade a reference instrument should make. If higher rates are ever needed,
the real fix is DCMI+DMA, which requires rewiring to the DCMI-mandated pins.

## Design notes

**GPIO polling, not DCMI.** The STM32F4's DCMI peripheral forces a specific
pinout (PA4/PA6/PB7 + scattered D0–D7). The wiring above uses a contiguous
`PC0..PC7` data bus instead, which DCMI cannot use — so capture is done by
polling. To make polling reliable the camera's own `CLKRC` prescaler divides
PCLK down to ~2 MHz, giving the 84 MHz core ~40 cycles per pixel byte. Frame
rate is irrelevant for a functional check; *not dropping samples* is what
matters.

**Bit-banged SCCB, not hardware I²C.** SCCB is not quite I²C: the OV7670 does
not support a repeated START, so a register read must be split into
write-then-STOP, then START-read. Hardware I²C blocks tend to fight that.
Bit-banging also keeps every edge under direct control.

**Pull-downs on all camera inputs.** These are a diagnostic necessity, not a
functional one. The OV7670 drives PCLK/VSYNC/HREF/data push-pull, so a
pull-down never fights a connected camera — but a *disconnected* pin left
floating picks up tens of kHz of ambient noise and reports as "active". That
false positive is precisely what this tool must never produce. With
pull-downs, disconnected reads as a clean zero.

**Register configuration** targets QQVGA 160×120 YUV422 — the same resolution
as the FPGA disparity pipeline, so the two can be compared directly. The
gamma curve, AEC windowing and histogram limits are taken from
[erikandre/stm32-ov7670](https://github.com/erikandre/stm32-ov7670) (Petr
Machala's tables), a working OV7670 bring-up on this exact Nucleo board;
without them the luma channel comes out flat and dim.

**Luma phase is detected, not assumed.** YUV422 interleaves luma and chroma,
and which byte of each pair is Y depends on the TSLB/COM13 ordering. The
firmware ships the raw pairs and the host script scores both phases
(neighbour correlation vs. dynamic range) and picks the one that looks like
a real image. `--phase 0|1` overrides it.

## Interpreting results

| Symptom | Meaning |
|---|---|
| `probe` all `[NO ACK]`, SDA reads 0xFF | nothing is pulling SDA low — camera unpowered or SCCB not wired |
| `probe` ok, `activity` all zero | camera talks but produces no pixel clock — check XCLK reaching the module |
| `activity` nonzero but `capture` times out | sync signals present but framing wrong — check HREF/VSYNC wiring |
| all three activity counts similar and in the tens of kHz | **floating inputs**, not real signals (this is what pull-downs now prevent) |
